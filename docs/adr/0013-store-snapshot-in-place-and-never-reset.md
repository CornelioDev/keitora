# 0013 — Overwrite the engine snapshot in place, and never reset or trust the database

- **Status:** Accepted
- **Date:** 2026-11-11

## Context

The service keeps blocklists, settings, history, block events and the engine snapshot ([ADR-0011](0011-validated-engine-snapshot.md)) in one SQLite file, `%ProgramData%\Keitora\keitora.db` (T-2.2). Three threats shape how it writes and reads that file:

- **A full disk** ([#48](https://github.com/CornelioDev/keitora/issues/48)). A standard user can fill the system volume, as NTFS keeps no space reserved for `SYSTEM`. If a strict session's snapshot can't be written, a reboot restores an older one, often an idle engine, and the strict session is gone. SQLite's default rollback journal (`DELETE`) creates a new journal file on every write, `TRUNCATE` regrows it, and `WAL` appends to a log: all of them need new disk space for every checkpoint.
- **A damaged or foreign file.** Until T-5.3 any user can edit or replace the file, and a newer Keitora may have migrated it. Many apps answer an unreadable or unknown database by recreating it; here that would also erase a strict session.
- **SQL and side files planted next to the data.** A database can carry triggers, views and virtual tables that run when the store reads or writes, and SQLite looks for a `keitora.db-wal` file before every read and uses it, even when the store never asked for WAL. Either lets whoever can write the folder change what the service reads or make its writes vanish.

## Decision

- **The rollback journal is kept** (`PRAGMA journal_mode = PERSIST`): after each commit SQLite zeroes the journal's header instead of deleting the file, so a later transaction that changes as many pages reuses its space. Every commit is flushed (`PRAGMA synchronous = FULL`), so `Store::save_snapshot` returning `Ok` means the snapshot is on disk. Temporary data stays in memory (`PRAGMA temp_store = MEMORY`).
- **The snapshot has a fixed-size slot**: one row of a table of its own, its JSON padded with ASCII spaces to exactly `MAX_SNAPSHOT_BYTES` (2048) bytes, which is valid JSON whitespace. Every save is an `UPDATE` of that row to a value of the same length, which SQLite overwrites in place on the same page, along with page 1 (the file's change counter). The slot fits in one 4 KiB page, so no overflow page is ever involved. Every write checks that it changed exactly one row.
- **Space is allocated by the first save.** The first save `INSERT`s the row into the table's existing root page and journals those same two pages, so after it the database file and the journal are as large as every later checkpoint needs. That first save may need new space and may fail; T-2.5 refuses to start a strict session when it does (#48). Any earlier save, such as an unlocked session's, has already allocated it.
- **Opening rebuilds the journal's space.** SQLite sets `journal_mode` and `synchronous` only after reading the schema, and that first read plays back the journal of a transaction a crash interrupted, in the default `DELETE` mode, which deletes the journal. So, once the schema is checked and migrated, `Store::open` journals the two pages a checkpoint changes (page 1, by rewriting `user_version`, and the snapshot's page, by an `UPDATE` that changes its bytes, since SQLite doesn't journal an unchanged page) and rolls that transaction back. The journal grows to the size a checkpoint needs, and the database file isn't written, as the changed pages never leave SQLite's cache. This is best effort: on a read-only file or a full disk it fails, is logged, and the store opens all the same.
- **The length of a stored snapshot is checked in SQL** (`octet_length`, read from the record's header) before the value is read or parsed; anything longer than `MAX_SNAPSHOT_BYTES` is refused. No value longer than 8 MiB is read at all (`SQLITE_LIMIT_LENGTH`), almost twice the largest valid blocklist's JSON.
- **Opening never writes the database file before it trusts it.** The connection is set up first with options that need no read of the file. The schema version (`PRAGMA user_version`) is read next, and a newer or negative one is refused. Then the schema must be exactly what the migrations up to that version create, object for object and SQL text included (`StoreError::UnexpectedSchema`). Only then are migrations applied. An up-to-date database file is never written by opening, so a store on a full disk or a read-only file still opens, and the service can restore a session from it.
- **No SQL in the file runs, and there is no WAL.** The connection turns off triggers and views (`SQLITE_DBCONFIG_ENABLE_TRIGGER`, `SQLITE_DBCONFIG_ENABLE_VIEW`) and trusted schema, turns on defensive mode and `cell_size_check`, all before the first read. The bundled SQLite is compiled with `SQLITE_OMIT_WAL` (`LIBSQLITE3_FLAGS` in `.cargo/config.toml`, with `force = true`), so a `keitora.db-wal` file is never opened, and a database whose header asks for WAL is refused as not a database.
- **The store never deletes, resets or downgrades a database.** A file that isn't a database or is damaged is an error, and a newer schema is `StoreError::SchemaTooNew`, with the file left byte for byte as it was. Repairing it is a person's decision.

## Alternatives considered

- **`DELETE`, `TRUNCATE` or `WAL` journal mode**: each needs new disk space on every write (above). The acceptance tests of T-2.2 fail with all three.
- **`PRAGMA locking_mode = EXCLUSIVE`, to keep the journal through crash recovery**: the journal then holds a different set of pages, so a checkpoint after a restart grows it (from 4616 to 8720 bytes in QA's test).
- **Re-saving the loaded snapshot to rebuild the journal**: SQLite skips a page whose bytes don't change, so nothing would be journaled. A commit that changes the bytes and changes them back would also write the database file at every start.
- **A separate snapshot file, written to a temporary file and renamed**: the temporary file needs new space on every write, and a second file means a second place to protect and keep consistent.
- **Preallocating the snapshot row when the database is created**: the first strict snapshot would need no new space either. But a new store must report that it has no snapshot, which needs a marker value the snapshot's JSON format doesn't have.
- **Recreating an unreadable database**: the usual answer for caches, but here it turns damage, or a planted file, into the end of a strict session.

## Consequences

- Checkpoints of a running session need no new disk space; only the first snapshot ever saved, and writes of other kinds (history, block events, blocklists), may. A failed checkpoint keeps the previous snapshot whole (T-2.5 keeps the session in memory and retries).
- After a crash during a write, the next start needs new disk space to rebuild the journal. If the disk is full then, checkpoints fail until there is space, while the last snapshot on disk stays whole, so the strict session isn't lost: it resumes from that snapshot after the next restart.
- The journal file `keitora.db-journal` stays in the data folder, as large as the biggest write so far (at least two pages and a header once a snapshot is saved); it is never truncated. Every start rewrites it.
- A snapshot's JSON can grow to 2048 bytes; the largest the engine writes today is about 250. Growing past that needs a new migration that enlarges the slot.
- A later migration can't use triggers or views, or the store would have to turn them back on.
- The WAL protection depends on how SQLite is built. Building with `LIBSQLITE3_SYS_USE_PKG_CONFIG` (a system SQLite) or another way of replacing `LIBSQLITE3_FLAGS` drops it. Release builds must use the bundled SQLite with the repository's `.cargo/config.toml`; a unit test fails if `OMIT_WAL` is missing from the build.
- A database planted with another page size may lose the in-place guarantee.
- **Until T-5.3, a planted journal is trusted.** Under `PERSIST`, a `keitora.db-journal` that a standard user creates before the database exists, and keeps open without `FILE_SHARE_DELETE` so that SQLite can't delete it, becomes the store's permanent journal. Its owner can later write a hot journal into it, which `SYSTEM` plays back into the database at the next open. T-5.3 closes this: before opening, the service checks that `keitora.db` and its `-journal`, `-wal` and `-shm` files are absent or are regular files owned by `SYSTEM` or Administrators, with no write access for users, not reparse points, and with a link count of 1, and it refuses a foreign journal.
- A damaged, newer or unexpected database can't be opened until someone repairs, restores or removes it; what the service does meanwhile is T-2.5's and T-2.7's to decide. That failure is visible, while silently losing a strict session isn't.
